## Deliver the reader experience

- Each eligible canonical series gets a stable identity and shareable address. Identity must include instrument/base/methodology and declared dimensions, and survive sorting, pagination and source refreshes. Reuse existing stable anchors where valid, with tested mappings. Do not derive identity from array position, search-row number or a changing display title. Deduplicate aliases only with evidence; preserve source lineage. Explain how identities behave when an instrument is replaced.
- A reusable indicator view: clear name/definition, geography/cuts, unit/frequency, full available history, latest observation and date, source and actual revision status, missing periods and instrument boundaries, accessible underlying table, date controls, selected-series CSV/JSON and SVG/PNG exports, copy link, parent-guide context and related series. Show one-period survey estimates as snapshots; never manufacture a history or change rate.
- Build compatible comparisons with shareable URL state, a useful curated set of examples and add/remove-series controls. Start with the same indicator across states, same-instrument CPI components or rural/urban survey cuts. Keep nulls as null, explicit date alignment, fiscal/calendar semantics, frequency aggregation and unit handling. No silent interpolation, base-year splicing, guessed Cartesian cross-tabs or misleading dual-axis defaults. Cross-frequency and unit transformations require deterministic, auditable definitions; unsupported combinations should explain their limitation. Cap chart complexity sensibly and document the measured choice.
- Links from guides/EveryCut and search should reach the exact indicator; retain guide context. Search-engine landing pages, canonical URLs, deep-link hydration and no-JS behavior must be deliberate. Addressable access to the long tail is separate from pre-rendering every page for SEO; do not hide omissions behind a headline catalogue.
- Preserve the refined editorial design and existing guides. The explorer supplements the explanatory product. No LLM-generated explanation per granular record, accounts, billing or elaborate formula language required for this first complete implementation.

## Performance and architecture

Do not create millions of Astro HTML/CSV files, ship an entire cube to open one series, or run a browser scan of the full catalogue for every query. Measure actual data shapes first. Compare static pre-rendering, a shared explorer with bounded first-party immutable data shards, and an on-demand cached Worker route. Choose the smallest operationally sound architecture that meets the whole scope, then implement it. A selected pre-rendered catalogue plus fully addressable long tail is a candidate, not permission to drop the tail. Set and enforce payload, request, memory, asset-count and rendering budgets based on measured cases. Assess cache invalidation, manifest/shard version consistency, stale deployment mixing, cold/warm behavior, mobile main-thread costs and deployment/build growth. Bounded work and cancellation are necessary for rapid navigation/search.

Owner authorizes the narrow architecture/contract evolution needed for this explorer, including lazy fetching of our own versioned, validated published static files or a justified Worker route. This does not authorize live government data fetching at reader time, abandoning static guides, bypassing numeric gates or silently rewriting contracts. Document the exact exception, rationale and enforceable tests in collaboration with the performance task. Prefer serving static assets directly; justify any R2/D1/KV or other paid service using measured need. Cloudflare Workers is the intended hosting direction; implementation must fit current asset/file/runtime limits. No infrastructure changes or DNS cutover in this task.
